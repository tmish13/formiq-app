## 1. `alembic heads` — the audit's multi-head risk is DISPROVEN

`AUDIT.md` §4.3 flagged, explicitly as **unverified**, that 41 scripts in
`backend/migrations/versions/_archived/` might pollute the version graph. Verified now:

```
$ docker compose exec -T app alembic heads --verbose
Rev: 0008_seed_exercise_templates (head)
Parent: 0007_add_training_sessions
Path: /app/migrations/versions/0008_seed_exercise_templates.py

$ docker compose exec -T app alembic branches
(no output)

$ docker compose exec -T app alembic history
0007_add_training_sessions -> 0008_seed_exercise_templates (head), Seed exercise_templates...
0006_add_squat_sessions -> 0007_add_training_sessions, Add training_sessions table...
0005_add_user_profile_fields -> 0006_add_squat_sessions, Add squat_sessions table.
0004_v1_stabilization -> 0005_add_user_profile_fields, Add weight_kg, age, height_cm...
0003_add_profile_fields -> 0004_v1_stabilization, V1 Stabilization...
0002_add_social_auth_fields -> 0003_add_profile_fields, Add fitness_goal...
0001_baseline -> 0002_add_social_auth_fields, Add social_provider and social_id...
<base> -> 0001_baseline, Baseline migration — creates all tables from current models.
```

**Exactly one head. Zero branch points. Eight revisions, linear.**

Mechanism: alembic 1.13.1 only recurses into subdirectories of `versions/` when
`recursive_version_locations` is set, and it is absent from `backend/alembic.ini`
(verified: `grep -c recursive_version_locations alembic.ini` → `0`). So `_archived/`
is invisible to alembic.

**Consequence for G-14:** the "multiple heads" half of that gap is closed — it was
never real. The other half is now *confirmed rather than suspected*: the 127
`create_index` calls in `_archived/` are definitively **not applied**, because
alembic cannot see them at all. The active chain creates 12 indexes.

`alembic upgrade head` then applied all 8 migrations cleanly and seeded the Squat
template:

## 2. Bring-up: five defects blocked `docker compose up` entirely

None of these were speculative — each one stopped the stack dead. Branch
`audit/day1-local-stack`, commit `71b6ae9`.

| # | Defect | Symptom | Fix |
|---|---|---|---|
| 1 | `worker` lacked the `uploads` volume that `app` mounts | with local storage the worker cannot see uploaded videos | add `uploads:/app/uploads` to worker |
| 2 | compose `SECRET_KEY` default is 27 chars; `Settings` enforces `min_length=32` (`app/core/config.py:177`) | `ValidationError` → `Worker failed to boot` | dev default ≥32 chars |
| 3 | `db` service defaulted `POSTGRES_DB=formiq_db`, app/worker connect to `formiq` | `Startup error: database "formiq" does not exist` | align both to `formiq` |
| 4 | `migrations/env.py` did `sys.path.insert(0, project_true_root)` | in-container that root is `/`; since `backend/__init__.py` exists, `import app` resolved to `/app` not `/app/app` → `ModuleNotFoundError: No module named 'app.models'` | `append` instead of `insert(0, …)` |
| 5 | `migrations/env.py` rewrote `POSTGRES_SERVER=db` → `localhost` unconditionally | `connection to server at "localhost" … refused` — in-container migrations impossible | only fall back when the `db` alias does not resolve |

**Defects 4 and 5 are not local-only.** `backend/docker-entrypoint.sh:33` runs
`alembic upgrade head` in production using this same image layout, so the
production migration step was broken by both.

### Also found, NOT fixed (out of Day 1 scope)

**The app creates tables outside Alembic.** `app/core/lifespan.py:99` calls
`init_db()` → `Base.metadata.create_all()` on startup. Once the app has booted
against a fresh database, `alembic upgrade head` fails with
`DuplicateTable: relation "exercise_templates" already exists`. The runtime schema
and the migration chain are therefore independent sources of truth. Correct
sequence today is: migrate *before* first app boot. Flagged for G-14 (Day 5).

## 5. Two causes of the train/serve gap, found by accident

Both matter for G-07 (offline F1 0.724 vs end-to-end F1 0.182) and both would
silently corrupt Day 4 and Day 6 numbers if left alone.

### 5a. MediaPipe silently runs at complexity 1, not 2 — in every container

```
Downloading model to /usr/local/lib/python3.11/site-packages/mediapipe/modules/pose_landmark/pose_landmark_heavy.tflite
MediaPipe Pose init failed at complexity=2 ([Errno 13] Permission denied:
  '.../pose_landmark_heavy.tflite'), falling back to complexity=1
```

```
$ ls -la .../mediapipe/modules/pose_landmark/
drwxr-xr-x 3 root root      4096 .
-rw-r--r-- 1 root root   6440512 pose_landmark_full.tflite     <- complexity 1, bundled
                                  pose_landmark_heavy.tflite   <- complexity 2, ABSENT
$ id
uid=1000(appuser) gid=1000(appgroup)
```

MediaPipe bundles the complexity 0/1 models but **downloads** the heavy
(complexity 2) model on first use. `backend/Dockerfile:60` switches to non-root
`appuser`, and `site-packages` is root-owned, so the download fails and the code
falls back — logged as a warning, never as an error.

`AI_MODEL_COMPLEXITY` defaults to **2** (`app/core/config.py:768-770`). So the
configured value is silently ignored in every container built from this
Dockerfile — **including production**.

Impact is large. For this exact video, `scripts/output/posture_v1_labels_and_results.csv`
records `complexity=2 → prob_fault=0.0001, confidence=1.000`. Measured here at
complexity 1: **`prob_fault=0.4739, confidence=0.052`** — against a `0.525`
threshold. Same video, same weights, nearly a coin flip instead of a confident
call.

The eval report was produced outside this container, at complexity 2. That is a
concrete reason its numbers do not reproduce in the deployed pipeline.

### 5b. The PostureV1 scaler is unpickled across sklearn versions

From the e2e test run:

```
/usr/local/lib/python3.11/site-packages/sklearn/base.py:376: InconsistentVersionWarning:
Trying to unpickle estimator StandardScaler from version 1.6.1 when using version 1.4.0.
This might lead to breaking code or invalid results.
```

`posture_v1_scaler.joblib` was fitted under scikit-learn **1.6.1**;
`requirements.txt:35` pins **1.4.0**. This scaler standardises all 151 features
before inference, so any silent behavioural difference lands directly on
`prob_fault`.

**Neither is fixed today** — both touch the image/pins and change model
behaviour, so they are your call. Recommendation: fix 5a before Day 4, since
every per-frame and accuracy number depends on which pose model actually runs.

## 7. G-13 — e2e pipeline test (branch `audit/g13-e2e-pipeline-test`, commit `e423a7f`)

`backend/tests/e2e/test_pipeline_completes.py`. Drives the real pipeline with
only S3 mocked and asserts a *result*, not just a terminal status:

- `FormCheck.status == COMPLETED`
- `results["posture_v1"]["decision"] ∈ {good_form, fault}` — rejects `"uncertain"`, which would mean a quality gate fired and no inference was applied (a vacuous pass)
- `prob_fault` is a real probability in [0, 1]
- `posture_score` is written (PostureV1 is its sole writer for squats)
- exactly **one** `posture_v1_inference_logs` row, with `latency_ms > 0`
- the known-good fixture classifies as `good_form`

```
======================== 1 passed, 31 warnings in 8.82s ========================
```

Two implementation notes:

- The test calls `_process_form_check_task_async` directly. The Celery wrapper
  (`analysis_tasks.py:437-441`) uses `asyncio.run()`, which cannot nest inside
  pytest-asyncio's running loop.
- **`--import-mode=importlib` is required in the container.** `backend/` is
  mounted at `/app` and contains `__init__.py`, so pytest's default *prepend*
  mode walks up past it and inserts `/` on `sys.path`, making `import app`
  resolve to `/app` instead of `/app/app` — the same root cause as bring-up
  defect 4. Symptom without it: `ModuleNotFoundError: No module named 'app.services'`
  while loading `tests/conftest.py`.

Prerequisites (one-time; `pytest-timeout` and `pytest-env` are in
`requirements-test.txt`, which the image does not install):

```bash
docker compose -f backend/deployment/docker-compose.yml exec --user root app \
  pip install pytest-timeout==2.2.0 pytest-env==1.1.1
docker compose -f backend/deployment/docker-compose.yml exec -T db \
  psql -U postgres -c "CREATE DATABASE formiq_test;"
```

Full command:

```bash
docker compose -f backend/deployment/docker-compose.yml exec \
  -e ENVIRONMENT=test \
  -e TEST_DATABASE_URL=postgresql+asyncpg://postgres:postgres@db:5432/formiq_test \
  -e REDIS_URL=redis://redis:6379/0 -e REDIS_HOST=redis -e REDIS_PORT=6379 \
  app pytest -m e2e tests/e2e/test_pipeline_completes.py \
  --override-ini="addopts=--asyncio-mode=auto" \
  --import-mode=importlib -p no:randomly
```
