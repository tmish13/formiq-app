## 0. What is being tested

The plan's Week-1 gate: *"a 300-video batch with beat running: 0 never-run, 0 flips, A1–A10 pass."*
Gate 1b found G-48 with beat running and was completed with beat stopped; this is the first batch
deeper than the reaper's 30-minute threshold to run with the reaper active since the fix.

What changed since Gate 1b (all bind-mounted into the running containers and picked up by
`docker compose restart worker beat app` at 22:35 PDT):

1. `maintenance_tasks.py` — the PENDING sweep is gated on the broker: one snapshot of the default
   queue and kombu's `unacked` hash per tick; a PENDING row whose id is in it is *deferred*; an
   unreadable broker defers every PENDING row. PROCESSING rows keep the age policy.
2. `analysis_tasks.py` — a `claimed` flag; a task that loses the claim writes nothing in its `finally`.
3. `form_check_service.py` — finalize is `UPDATE … WHERE status = PROCESSING` with a rowcount check;
   feedback rows are replaced only after the status write succeeded.
4. `trail_report.sh` — A10: a terminal row must agree with its latest closed run, and no video is
   judged twice for real.
5. `image_check.py` — every worker process now logs at start that the image is missing
   `pytest-timeout` (G-43), which is the truth.

## 2. Two batches, because the first one did not exercise the gate

Batch 1 (300 videos, 22:36–23:03 PDT) drained in 27 minutes: no row ever sat in the queue for 30
minutes, so the reaper never had a PENDING candidate and the broker gate was never exercised. It
did exercise the other half: two worker children were OOM-killed (G-46), Celery redelivered their
messages, and the worker logged for both

```
[CeleryTask] FormCheck b81a8139-… could not be claimed (status: processing). Skipping …
[CeleryTask] FormCheck b81a8139-… was never claimed by this task; row left untouched (G-48).
```

— the exact path that flipped 520 rows to FAILED in Gate 1b, now a no-op. A gate that is not
exercised is not passed, so batch 2 (600 videos, 23:05–00:40 PDT, 2-second submission stagger
against ~7 videos/minute) put the queue more than 40 minutes deep.

## 4. Worker kills, and what they cost now

Seven OOM kills in 900 videos (0.8 %, G-46's rate; clustered late in each batch, the memory-growth
signature). Each cost a **30-minute wait** for the reaper's PROCESSING retry instead of a lost row:
the redelivered message is refused at the claim and leaves the row alone, the reaper re-dispatches
it at the threshold, the retry completes. Seven runs closed as `abandoned` by the reaper (three on
its own 60-minute schedule, four by the logged 5-minute call in `bench/abandon_dead_runs.py` so this
report could be produced tonight). The next step (plan D2a, `audit/worker-lost-reclaim`) is to
reclaim on redelivery — seconds, with `error_type = worker_lost` on the trail — and to recycle worker
children so the kills stop clustering.
