## 2. G-22 — measured first, and it is NOT a corruption

The concern was that unpickling `StandardScaler` across scikit-learn versions
(fitted 1.6.1, runtime pinned 1.4.0) might be silently shifting all 151 features.
Measured before touching the pin:

```
sklearn runtime       : 1.4.0
n_features_in_        : 151   (manifest feature_dim 151)

mean_  min/max        : -0.025551434277330382   175.50432687135222
manifest mean_range   : [-0.025551434277330382, 175.50432687135222]
scale_ min/max        : 0.026816585489101073    33.92105597991595
manifest std_range    : [0.026816585489101073,  33.92105597991595]

mean_  matches manifest: True
scale_ matches manifest: True
non-finite params      : False
```

**Bit-identical to the statistics recorded at fit time** (atol 1e-12).
`StandardScaler.transform` is `(X - mean_) / scale_` — pure numpy over fitted
attributes, and those attributes survived the cross-version unpickle exactly.

**Conclusion: G-22 contributes nothing to the train/serve gap.** It remains a
real hygiene risk (a future sklearn could change the pickle format or the
attribute semantics), but bumping the pin to 1.6.1 would have been a dependency
change across `xgboost`, `sentence-transformers` and the RandomForest artifacts
taken on faith, for zero measured benefit.

Action taken instead: assert the invariant continuously, so if it ever *does*
break the test fails rather than the score silently drifting. See §5.

## 3. G-21 — the actual defect

```
Downloading model to /usr/local/lib/python3.11/site-packages/mediapipe/modules/pose_landmark/pose_landmark_heavy.tflite
MediaPipe Pose init failed at complexity=2 ([Errno 13] Permission denied:
  '.../pose_landmark_heavy.tflite'), falling back to complexity=1
```

MediaPipe bundles complexity 0/1 but downloads the heavy model on first use.
`backend/Dockerfile:60` switches to non-root `appuser`; `site-packages` is
root-owned. The download fails, `ai_service.py:95-105` catches it, logs a
**warning**, and serves complexity-1 keypoints to a model evaluated on
complexity-2 keypoints.

Fix (`backend/Dockerfile`, after `pip install`, still as root):

```dockerfile
RUN python -c "import mediapipe as mp; p = mp.solutions.pose.Pose(model_complexity=2); p.close()" \
    && test -f /usr/local/lib/python3.11/site-packages/mediapipe/modules/pose_landmark/pose_landmark_heavy.tflite \
    && chmod -R a+rX /usr/local/lib/python3.11/site-packages/mediapipe/modules
```

The `test -f` makes the build **fail loudly** rather than shipping an image that
will silently fall back at runtime.

### Gotcha worth recording

`docker compose build app` builds **only** the app image. The `worker` service
has its own `build:` block and therefore its own image. After rebuilding only
`app`, the worker kept running the old image and kept falling back — the app
container reported complexity 2 while the worker reported 1. **`docker compose
build` (no service argument) is the correct command.**

### After

```
$ ls -l .../pose_landmark/pose_landmark_heavy.tflite     # in BOTH app and worker
-rw-r--r-- 1 root root 27709200 pose_landmark_heavy.tflite

$ python -c "from app.services.ai_service import AIService; a=AIService(); ..."
complexity_used    : 2
fallback_triggered : False
```

## 4. Effect on the model's output — same video, same weights

`backend/test_videos/good/T6ad8Et3C5Q_good_rep_1.mp4`, read from the DB after a
full upload → Celery → inference run:

| | before (cx 1) | **after (cx 2)** | eval CSV (cx 2) |
|---|---|---|---|
| `model_complexity` | 1 | **2** | 2 |
| `pose_complexity_fallback` | true | **false** | — |
| `prob_fault` | 0.4739 | **0.3347** | 0.0001 |
| `confidence` | 0.052 | **0.3306** | 1.000 |
| `posture_score` | 55 | **62** | — |
| `decision` | good_form | good_form | good_form |
| PostureV1 latency | 464.9 ms | 320.1 ms | — |
| sequence_length | 90 | 90 | 89 |

**Direction confirmed.** `prob_fault` moved away from the 0.525 threshold
(0.4739 → 0.3347, margin 0.051 → 0.190) and confidence improved 6.4×. The
classification was `good_form` in both cases, but it was nearly a coin flip
before and is now a real call.

**It did NOT return to the eval CSV's 0.0001 / confidence 1.000.** That residual
gap is large and currently unexplained — see G-25 below. Do not describe G-21 as
having "closed" the train/serve gap; it closed one measured contributor.

Note the PostureV1 latency *fell* (464.9 → 320.1 ms). That figure times the
CNN-LSTM forward pass only, not MediaPipe, so it is warm-cache noise rather than
a complexity effect. Complexity 2 is slower where it matters: the e2e test went
from 8.82 s to 15.67 s.

## 6. New gaps found while doing this

### G-24 — the manifest's `feature_order` does not describe the code

Writing the feature-order test surfaced a documentation/implementation mismatch.
The manifest says:

```
"0_32":  "joint{0..32}_x_mean"      (33 joints, x only)
"33_65": "joint{0..32}_x_std"
```

`features_151d.get_feature_names()` actually emits:

```
[0:33]   joint{0..10}_{x,y,z}_mean   (11 joints x 3 coords)
[33:66]  joint{0..10}_{x,y,z}_std
```

Both are 33 values, so the 151 total still lines up and nothing crashes — which
is why it went unnoticed. Blocks 3-5 (ranges, 4 angles x 15 stats, 4 derived)
**do** match the manifest.

Serving is self-consistent: the same function builds the vector every time. The
risk is that the manifest is the *only* written record of what training used, and
for the first 66 of 151 features it is demonstrably not an accurate description
of the serving code. If training genuinely used `joint{0..32}_x_*`, then 66
features are misaligned and that would dwarf G-21. **Cannot be resolved from this
repo** — it needs the training notebook.

The test now pins the real layout, so at least drift is caught going forward.

### G-25 — residual eval gap after G-21

Complexity 2 restored, yet `prob_fault` is 0.3347 vs the eval CSV's 0.0001 on the
same file. Candidate causes, none yet tested:

- the eval script fed the file directly; the pipeline path adds upload → S3 key → decode
- `sequence_length` 90 here vs 89 in the CSV — an off-by-one in frame decode
- MediaPipe/OpenCV version or aarch64-vs-x86 numerical differences
- G-24, if the feature order genuinely differs from training

Worth one focused session before Day 6, since every accuracy number depends on it.
